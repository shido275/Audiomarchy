# The audio engine

Audiomarchy does not replace PipeWire. It configures it the way a studio
expects, and gives you one command to check and change it.

## The graph

PipeWire is the server. WirePlumber is the policy layer that creates nodes for
ALSA devices and decides their properties. `pipewire-pulse` serves PulseAudio
clients, `pipewire-jack` serves JACK clients. A DAW can use any of the three
and they all land in the same graph.

The engine settings live in two places:

```
~/.config/pipewire/pipewire.conf.d/90-audiomarchy.conf
~/.config/wireplumber/wireplumber.conf.d/90-audiomarchy.conf
```

The first is generated by `audiomarchy audio latency`; do not hand-edit it,
because switching profiles rewrites it.

## Buffer size and latency

PipeWire processes audio in *quanta*. One quantum is one scheduling period, so
the one-way latency contributed by the buffer is:

```
latency (ms) = quantum / sample-rate * 1000
```

At 48 kHz:

| Quantum | Per period | Typical round trip* |
|---|---|---|
| 64 | 1.33 ms | ~4 ms |
| 128 | 2.67 ms | ~7 ms |
| 256 | 5.33 ms | ~13 ms |
| 1024 | 21.33 ms | ~45 ms |

\*Round trip includes the interface's own buffering and the DAW's. Measure it
with a loopback test if it matters; do not trust the table.

A smaller quantum is not automatically better. Every period is a deadline, and
missing one is an xrun. If `audiomarchy doctor` reports xruns, fix load first
(background sync, browser tabs, an unplugged power supply), then raise the
quantum.

## What the tuning actually does

`90-audiomarchy.conf` sets:

- `default.clock.rate = 48000` — one rate for the graph, so plugins are not
  resampled.
- `default.clock.allowed-rates = [ 44100 48000 88200 96000 ]` — devices at
  other rates can still be the driver without a forced resample.
- `default.clock.quantum = 256` — the default profile.
- `default.clock.min-quantum = 32` — a DAW can ask for tighter buffers
  without editing config.
- `default.clock.max-quantum = 2048` — headroom for big graphs.

The WirePlumber drop-in sets `session.suspend-timeout-seconds = 0` on all
nodes and adds `api.alsa.headroom = 1024` to ALSA devices. Suspension is the
one that bites: the default is a few seconds, after which WirePlumber parks an
idle interface and the next note is late or missing.

## Realtime scheduling

A DAW thread has to wake up on a deadline. Without realtime priority the
kernel can schedule a compiler or a browser render in front of it, and the
result is an xrun no buffer size will fix.

`realtime-privileges` provides a `realtime` group with:

```
rtprio   95
memlock  unlimited
nice     -19
```

The installer adds your user to that group. PAM applies limits at login, so a
user added today does not get them until the next login. That is why
`audiomarchy doctor` checks the *effective* `ulimit -r`, not group membership
alone.

## USB interfaces

USB audio-class devices are subject to USB autosuspend. When the kernel
suspends one, it disappears from the graph. `audiomarchy device usb-power on`
walks `/sys/bus/usb/devices`, finds interfaces with class `01` (audio), and
sets the parent device's `power/control` to `on`.

That setting does not survive a reboot. Re-run it after replugging, or add it
to your session startup. `audiomarchy doctor` warns when an interface is still
set to `auto`.

## The virtual loopback

`90-audiomarchy-loopback.conf` loads two PulseAudio-compatible modules at
`pipewire-pulse` start:

- `module-null-sink` → **Audiomarchy Loopback**
- `module-remap-source` from its monitor → **Audiomarchy Loopback Mic**

Select the sink as an application's output to capture it silently; record from
the mic to capture it. `audiomarchy device loopback off` renames the config to
`.disabled` and restarts `pipewire-pulse`.

## Diagnosing xruns

1. `audiomarchy doctor` — limits, quantum, device suspension, sampled xruns.
2. `rtcqs` — a deeper, opinionated realtime checklist.
3. `pw-top` — watch `ERR` and `BUSY` per node while the problem happens.
4. `journalctl --user -u pipewire -u wireplumber -b` — driver changes and
   device errors.

Common causes, in order: a browser or Electron app with a busy render loop,
USB autosuspend, a device switching sample rate mid-session, and a quantum
that is simply too small for the plugin load.

## Optional: a realtime kernel

The stock Arch kernel is fine for most interfaces. If you have tried
everything and still see xruns under load, `linux-rt` is the next step. It is
not installed by default because it is a large, invasive change and it is not
a magic fix for a badly configured graph.
